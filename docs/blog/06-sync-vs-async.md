# 从抢课到秒杀（六）：同步还是异步？高并发写入的架构决策框架

> 本文是《从抢课到秒杀》系列的第六篇，演进篇的开始。
> 前面五篇反复说"TalentHub 这个量级同步就够了"——这一篇把"够了"量化，
> 并回答那个终将到来的问题：并发涨到多少、出现什么信号时，才值得把链路改成异步。

## 一、先算清楚：同步链路的能力边界在哪

"同步扛不住高并发"是一句流传很广但从不给数字的断言。我们来实际算一算，同步链路的瓶颈到底在哪、大概是多少。

TalentHub 的同步链路是：限流 → Redis Lua 预扣 → DB 事务（upsert + 条件 UPDATE）。逐段看容量：

- **限流与预扣**：Redis 单实例 10 万+ QPS，单次 Lua 亚毫秒。在几千 QPS 的场景里它连热身都算不上，不讨论。
- **DB 事务**：这才是瓶颈——但要说清楚瓶颈的**形状**。

第三篇讲过，同一门课程的所有成功扣减都在竞争 `course` 表的同一把行锁，串行执行。于是单课程的落库吞吐上限是一道除法题：

```
单课程扣减 TPS 上限 ≈ 1000ms / 热点行锁持有时长(ms)
```

锁持有时长 = 条件 UPDATE 的执行时间 + 事务提交（含 WAL 刷盘）。普通云盘上 fsync 约 1~2ms，本地 NVMe 或组提交摊薄后可到 0.5ms 以内。粗算：**单一热点行的扣减上限在每秒几百到一两千次这个量级**。

现在把业务数字放进来：一门课库存 20~200，Redis 预扣层保证到达数据库的写请求约等于库存量。也就是说，哪怕这门课瞬时来了 5 万人，数据库要串行处理的也只有 200 次扣减——**不到一秒的活**。多门课同时开抢？不同课程是不同的行锁，天然并行。

结论先立在这里：**同步链路的瓶颈是"单一热点行的串行扣减"，而 Redis 预扣层已经把这个瓶颈的输入压到了库存量级。** 只要"库存量 ≪ 热点行每秒吞吐"，同步就绰绰有余。

那什么时候会不够？两种情形：

1. **库存本身巨大**：单品库存几万、且要求秒级卖光（电商大促的形状）——到达 DB 的合法写入就有几万次，串行扣减要几十秒，链路 RT 飙升。
2. **防线前移失效**：没有 Redis 预扣层（或它挂了走降级），洪峰直接怼到数据库。这时的死法不是行锁，而是**连接池雪崩**：热点行排队 → 事务变慢 → 连接归还变慢 → 池耗尽 → **所有接口**（包括和抢课无关的）拿不到连接 → 全站超时。第三篇把报名连接池收紧到 30，就是给这条雪崩路径设的隔离舱。

## 二、同步与异步：把优缺点摊开

把两种架构放在一张桌子上：

**同步（TalentHub 现状）**：请求穿过整条链路，拿着最终结果返回。

| 优点 | 缺点 |
|---|---|
| 结果即时：用户点完立刻知道成没成 | 吞吐上限受制于链路最慢环节（DB 热点行） |
| 链路短，故障域清晰，排障是单请求视角 | 无削峰能力：洪峰原样传导到每一层 |
| 无消息组件：没有可靠性三件套要维护 | 下游抖动直接放大为用户可见的失败/超时 |
| 状态天然一致：成功=已落库，无中间态语义 | 扩容只能整条链路一起扩 |

**异步（MQ 削峰）**：请求在 Redis 预扣成功后投递消息即返回"排队中"，订单服务按自己的节奏消费落库。

| 优点 | 缺点 |
|---|---|
| 削峰：洪峰变堆积，下游永远匀速（漏桶的架构版） | 结果不即时：要建状态查询/推送，前端要轮询 |
| 上下游解耦：DB 抖动不影响接单，只影响出结果的速度 | 消息可靠性三件套：发送确认、持久化、消费重试+死信 |
| 吞吐弹性：加消费者就是加吞吐（分区数内） | 消费幂等必须做（消息至少一次投递） |
| 故障隔离：下单服务挂了，请求还在队列里等它复活 | 新增一整个有状态组件的运维：堆积监控、rebalance、容量规划 |
| | 超时未消费的名额回补：一条全新的逆向链路 |

注意异步的缺点列表更长——这不是修辞倾向，是事实：**异步买到的是吞吐与稳定性，付出的是一整套新的状态管理**。"排队中"是一个此前不存在的业务状态，它需要存储、需要查询接口、需要超时策略、需要与预扣名额的生命周期绑定。很多团队只看到了"MQ 削峰"四个字，没看到后面拖着的这串账单。

还有一个常被忽略的镜像事实：**同步架构里其实也有"队列"**——连接池的等待队列、Tomcat 的工作线程队列。区别在于这些队列容量小、无持久化、溢出即失败。异步化的本质不是"引入队列"，而是**把队列显式化、持久化、并让它的深度成为可运营的指标**。理解了这一点，两种架构就不是非黑即白，而是同一根轴上的两个位置。

## 三、决策框架：四个维度，看信号不看情怀

架构选型最忌"我觉得会有高并发"。给一个可操作的清单——四个维度，每个都有具体的检查方法：

**① 峰值写入 vs 热点容量。** 算两个数：到达 DB 的峰值合法写入量（有预扣层时 ≈ 库存量；没有则 ≈ 峰值 QPS），和热点行每秒吞吐（几百~一两千）。前者除以后者，得到"洪峰需要几秒消化"。**小于 1 秒，同步；超过 5~10 秒，用户已经在超时边缘，异步开始有意义。**

**② 结果时效要求。** 用户能不能接受"排队中，稍后出结果"？抢课/内部审批：不能，员工就站在页面前等。电商下单：能，"排队中"甚至是秒杀氛围的一部分。**时效要求是硬约束——用户等不了，异步就不在选项里，无论并发多大**（那种情况的出路是第一篇提过的分桶等纵向优化，而不是异步）。

**③ 下游的脆弱度。** 下游是自己的 DB（可扩容、有连接池隔离），还是不可控的外部系统（老 ERP、第三方接口、每秒只能吃 200 请求的遗留服务）？**下游越不可控，MQ 作为缓冲层的价值越大**——这时引入 MQ 甚至不是为了吞吐，是为了把"下游挂了"从"我也挂了"变成"我先攒着"。

**④ 团队的运维成熟度。** 有没有人管 MQ 集群？堆积告警、死信处理、消费者 rebalance 排障，这些是长期成本。一个没有消息中间件运维经验的团队仓促上 MQ，通常收获的不是削峰，是凌晨三点的堆积告警和无人认领的死信队列。

四个维度过一遍 TalentHub：① 洪峰消化 <1 秒；② 用户要即时结果；③ 下游是自家 PG；④ 演示项目无运维预算。**四个维度全部指向同步**——这不是保守，是清单的每一项都在说同一句话。

反过来，什么信号出现时应该重新评估？给三个具体的触发器：

- 单课程库存需求涨到数千以上，且开抢后要求分钟级内出完结果；
- 落库下游从自家 DB 变成了不可控系统（比如报名要同步写集团统一的人力资源中台）；
- 监控里出现持续的连接池等待（`hikaricp_connections_pending` 高峰期非零）——同步链路开始顶到天花板的第一征兆。

## 四、不是二选一：中间还有半异步

最后拆掉"同步 vs 异步"这个二元对立本身。真实的设计空间是一条谱：

```
全同步 ────── 半异步 ────── 全异步
用户等待整条链路   用户等待关键段落     用户只等接单
```

**半异步**是最值得了解的中间形态：同步完成"定胜负"的部分（Redis 预扣——用户立刻知道抢没抢到名额），异步完成"记账"的部分（DB 落库、发通知、同步下游系统）。用户体验几乎无损（预扣结果就是最终结果的可靠预告），而最慢的落库环节获得了削峰能力。

它的代价是一个微妙的语义变化：**"抢到了"从"已落库"变成"预扣成功且最终会落库"**——这要求预扣到落库之间的消息投递高度可靠，且落库失败的回补链路（第四篇那套）要重新适配异步语义。天下没有免费的午餐，但半异步的性价比在很多场景里是三者中最高的。

TalentHub 如果要演进，第一站就是半异步。下一篇（第七篇）就以它为蓝图，把 MQ 削峰的完整链路设计摊开：消息怎么投、幂等怎么做、"排队中"状态怎么管、超时名额怎么回补。

## 五、小结

| 问题 | 本文的答案 |
|---|---|
| 同步的瓶颈在哪 | 单一热点行的串行扣减，上限每秒几百~一两千次 |
| 为什么 TalentHub 同步够用 | 预扣层把 DB 输入压到库存量级，洪峰消化 <1 秒 |
| 同步最危险的死法 | 不是行锁慢，是连接池雪崩拖垮全站——所以要隔离舱 |
| 异步买什么、付什么 | 买吞吐与故障隔离；付状态管理、消息可靠性、幂等、运维 |
| 怎么决策 | 四维清单：洪峰消化时长、结果时效、下游脆弱度、运维成熟度 |
| 二选一吗 | 不是。半异步（同步定胜负 + 异步记账）常是性价比最优解 |

这套框架里没有出现"高并发就该上 MQ"这样的句子——**架构决策的输入是可测量的信号，不是场景的名字**。下一篇进入异步世界的工程细节。
