# 从抢课到秒杀（四）：一致性工程——回补、反查与对账的边界感

> 本文是《从抢课到秒杀》系列的第四篇，也是技术浓度最高的一篇。
> 前两篇分别讲了 Redis 预扣和数据库最终防线，各自都是对的——
> 但把两个存储串在一条链路上，才是分布式问题真正的开始。

## 一、不一致窗口在哪里

回顾主链路：请求先在 Redis 扣掉一个名额（预扣），再去数据库落库。从预扣成功到事务提交之间，存在一段**中间态**：Redis 说这个名额没了，数据库还不知道。

正常情况下这个窗口只有几毫秒，提交后两边对齐。但数据库可能失败——事务回滚了，Redis 里那个名额却已经扣掉。如果放着不管，就是**永久少卖**：热门课程明明还有座位，页面却显示"已抢完"。

先回答一个前置问题：**为什么方向必须是"先 Redis 后 DB"？** 假设反过来，先落库再扣 Redis：DB 成功、Redis 扣减失败时，Redis 库存**虚高**——它会继续放行多余的请求打向数据库。虽然最终防线拦得住超卖，但你亲手制造了一个持续放大的窗口。而"先 Redis 后 DB"失败时的中间态是库存**虚低**——表现为少卖，符合第一篇的原则：

> 中间态只允许偏向"少卖"。方向选择不是习惯问题，是原则的推论。

同理，**取消报名的方向恰好相反**：先 DB 回加库存、后回补 Redis。两个方向的共同点是——中间态里 Redis 库存永远 ≤ 真实可卖量。

剩下的问题就是：DB 失败后，怎么把 Redis 里的名额还回去。听起来简单，做对却要分三种情况。

## 二、DB 失败的三副面孔

TalentHub 的 `EnrollmentServiceImpl` 把事务失败拆成三个分支处理。它们的区别不在代码量，在**你对"失败"知道多少**。

### 分支 A：upsert 返回 0 —— "他其实已经报上了"

上一篇讲过，`ON CONFLICT` upsert 返回 0 只有一种含义：该用户已持有有效报名。什么时候会走到这？该用户的并发双请求同时穿过了 Redis 判重的极端窗口，或者 Redis 集合数据曾经丢过。处理：

```java
if (e.getResultCode() == ResultCode.ALREADY_ENROLLED) {
    stockCacheService.rollbackPreDeduct(courseId, userId);  // 回补本次预扣
    stockCacheService.addUserBack(courseId, userId);        // 把用户补回集合
    return EnrollResultVO.alreadyEnrolledResult();          // 对用户是成功语义
}
```

两个细节：本次预扣要回补（这个请求没占成名额），但用户要**重新 SADD 回集合**——他确实持有一个名额（上一次成功的那次），集合必须与 DB 对齐，否则第二篇那条"扣减数 == 集合成员数"的不变量就破了。对用户返回"您已报名该课程"而不是报错——重复提交在用户视角是成功，不是失败。

### 分支 B：扣库存返回 0 —— "Redis 说有，DB 说没了"

预扣都成功了，DB 却售罄？说明 Redis 库存**虚高**（比如运维误操作改过 key，或某次回补多算了）。处理：回滚事务、回补预扣、对用户返回"名额已满"，同时打一条**一致性告警日志**——这个分支每出现一次，都意味着上游某处有 bug 或脏数据，值得人看一眼。差异的根治交给对账任务（第四节）。

### 分支 C：异常了 —— "我不知道成没成功"

前两个分支的失败是**确定的**（affected rows 说得清清楚楚）。分支 C 是超时、连接中断这类异常——而这里藏着整篇文章最重要的一个认知：

> **超时不等于失败。** 请求可能已经到达数据库并提交成功，只是响应没回来。

如果把超时当失败、无脑回补 Redis，就可能出现：DB 里报名成功了，Redis 却把名额还了回去——库存虚高，正是我们最不想要的方向。所以分支 C 的第一动作不是回补，是**反查**：

```java
private EnrollResultVO handleUnknownFailure(long userId, long courseId, Exception cause) {
    log.error("课程 {} 用户 {} 报名事务结果未知", courseId, userId, cause);
    try {
        if (enrollmentMapper.existsActive(userId, courseId)) {
            return EnrollResultVO.success();     // 原来成功了，直接返回成功
        }
        stockCacheService.rollbackPreDeduct(courseId, userId);  // 确认失败，才回补
    } catch (Exception query) {
        // 反查也失败：宁可暂时少卖，不回补，留待对账任务兜底
        log.error("[一致性告警] 反查失败，留待对账兜底: course={}, user={}", courseId, userId, query);
    }
    throw new BizException(ResultCode.SYSTEM_BUSY);
}
```

决策树是一条严格的偏好链：**确认成功 > 确认失败后回补 > 什么都不确认时按兵不动**。反查也失败（DB 可能整个抖了）时，正确动作是"不动"——回补可能错（万一 DB 成功了），不回补最多少卖，而少卖有兜底。每一步都在往"少卖"侧倾斜，这就是原则落到代码里的样子。

### 回补本身也会失败

三个分支都依赖"回补 Redis"这个动作，而它自己也可能失败（Redis 抖动）。TalentHub 的处理：本地重试 3 次、间隔 100ms，仍失败则打告警日志放弃。敢重试的底气来自第二篇：**rollback.lua 以 SREM 判资格，天然幂等**——重试一百次也不会把库存加多。敢放弃的底气来自下一节：对账任务会兜住。

幂等、重试、兜底，三者是一个整体：没有幂等就不敢重试，没有兜底就不敢放弃。

## 三、同步回补是主角，对账只是兜底

一个常见的架构误区值得单独敲打：把"定时对账任务"当成一致性的**主要手段**——主路径失败了不管，反正对账会修。

这个思路的问题在于**窗口期**。对账每 30 秒跑一轮，意味着差异最长存在 30 秒。抢课高峰恰恰集中在开抢后的前几十秒，热门课程在这个窗口里显示"已抢完"，活动结束了名额还空着——对账修好了库存，修不回用户的机会。

所以 TalentHub 的定位是：**主路径同步回补负责 99.9% 的场景（毫秒级修复），对账任务只兜"回补本身也失败"的残留（30 秒级修复）**。健康状态下，对账任务每一轮的发现应该是零差异——它像烟雾报警器，常年沉默，一响必有事。

## 四、对账任务的边界感

兜底任务看似简单（比一比、改一改），实际上每一个动作都要克制。`StockReconcileJob` 的设计有四条规矩：

**① 先验 DB 自身，再谈 Redis。** 对账以 DB 为基准，那 DB 自己错了怎么办？每轮先交叉验证：

```
course.stock 必须等于 total_quota - COUNT(有效报名)
```

不等，说明 DB 侧事务逻辑有 bug——此时**停止本轮修正**并强告警。基准都不可信了，任何"修正"都是把错误抄写一遍。

**② 只做单向修正，且两个方向待遇不同。**

- **Redis 虚高（redis > db）：立即修。** 虚高会放多余请求打 DB，是危险方向；修正的最坏代价只是几个请求被最终防线拦住，零风险。
- **Redis 虚低（redis < db）：连续两轮仍在，才修。** 这是关键的克制——虚低可能根本不是故障，而是**在途请求**：某个请求刚扣完 Redis、还没提交 DB，对账任务恰好在这一瞬间来比对。立刻"修正"等于把人家合法预扣的名额抢回来，反而制造真正的不一致。连续两轮（约 60 秒）仍存在的差异才可信为残留故障。

  兜底系统的第一戒律：**分得清"故障的中间态"和"正常的中间态"。** 分不清的兜底比没有兜底更危险。

**③ 修复即重建，复用预热路径。** 修正不是对库存数字做加减（加减需要知道差异的成因，而兜底恰恰面对的是成因不明的残留），而是整体重建：以 DB 为准重写库存 key、重建用户集合——和第二篇的"预热"是同一个操作。**修复 = 让 Redis 回到 DB 的投影**，一个心智模型覆盖两个场景。

**④ 不允许静默纠错。** 每次修正落库 `reconcile_log` 审计表（课程、修正前后值、动作类型、时间），管理端可查。一个会悄悄改数据的定时任务是排障时最大的噩梦——当你发现数据"自己变了"，你需要知道是谁、凭什么。

## 五、把整篇压缩成一张决策表

| 场景 | 你知道什么 | 动作 | 倾向 |
|---|---|---|---|
| upsert = 0 | 确定：用户已报名 | 回补 + 用户补回集合，返回成功语义 | 对齐 |
| 扣库存 = 0 | 确定：Redis 虚高 | 回补 + 告警，等对账根治 | 少卖 |
| 异常/超时 | **不确定** | 先反查；确认失败才回补；反查失败按兵不动 | 少卖 |
| 回补失败 | 确定：残留少卖 | 幂等重试 ×3，放弃则交对账 | 少卖 |
| 对账见虚高 | 确定：危险方向 | 立即以 DB 重建 + 审计 | 对齐 |
| 对账见虚低 | **可能是在途** | 观察两轮再重建 + 审计 | 容忍 |

通读这张表会发现，全部复杂度都来自同一个母题：**在信息不完整的情况下，选择犯哪一种错。** 这套系统的每一处选择都偏向同一侧——宁可少卖。方向一致，系统的行为就可预测；行为可预测，故障就可推理。所谓一致性工程，工程的从来不只是数据，还有决策。

至此，系统实录部分（架构、预扣、防超卖、一致性）完整落幕。下一篇换个节奏，做一次组件级的纵深：从系统里那 30 行限流 Lua 出发，把服务限流这个主题——四大算法、单机与分布式方案、阈值与拒绝策略——一次讲透。
