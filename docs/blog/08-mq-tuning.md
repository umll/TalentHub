# 从抢课到秒杀（八）：异步化实战（下）——让 MQ 跑在你想要的 QPS/TPS 上

> 本文是《从抢课到秒杀》系列的第八篇。上一篇把 MQ 削峰的链路设计付清了账单，
> 留了一个问题：消费速率"配成 300"这四个字，具体是怎么配出来的？
> 这一篇全是干货算术与参数——异步系统的性能不靠玄学，靠把三道乘法算对。

沿用上一篇的场景：抢课洪峰 2 万条报名消息入队，下游集团中台每秒只能承受 **300 TPS**。目标很明确：让消费端稳定跑在 300/s——快了打挂中台，慢了用户等太久。以这个目标贯穿全文。

## 一、先算账，再调参：三道乘法

拿到"目标 TPS"后，第一件事不是翻参数文档，是算三个数。

**第一道：并发度需求。**

```
所需并发度 = 目标 TPS × 单条处理耗时(秒)
```

单条消息的处理 = DB 落库(~5ms) + 写中台(~50ms) + 杂项 ≈ 60ms。要跑 300 TPS：`300 × 0.06 = 18` ——需要约 18 个并发处理单元（线程）。这个数字是一切配置的锚点。

**第二道：并发度上限。**

MQ 的并行度不是想开多少开多少，**队列/分区数是消费并行的硬上限**：RocketMQ 里一个队列同一时刻只被消费组内一个消费者持有（队列内再由消费线程并行，见下节），Kafka 里一个分区只能被组内一个 consumer 线程消费。所以：

```
Topic 队列/分区数 ≥ 预期最大消费者实例数 × 留量系数
```

分区少了，加再多消费者实例也是空转（分不到分区）。经验做法：按未来 2~3 倍扩容预期设分区数（比如 3 实例 × 深度 2~3 → 8~12 个分区）。分区数上调容易下调难（Kafka 不支持缩分区），宁多勿少，但也别上千——分区太多推高 Broker 的文件句柄与选主开销。

**第三道：堆积消化时间。**

```
消化时间 = 堆积量 / (消费 TPS − 持续生产 TPS)
```

2 万堆积、消费 300/s、洪峰后生产归零：约 67 秒消化完。这个数决定了你对用户承诺的"报名确认预计时间"，也是告警阈值的依据（堆积 > 消费能力 × 可容忍延迟，就该报警）。

三道算完，参数只是把算出来的数字填进去。

## 二、RocketMQ：把消费速率钉在 300 的三板斧

**板斧一：并发线程数——粗调。**

```java
consumer.setConsumeThreadMin(18);
consumer.setConsumeThreadMax(18);
```

直接把第一道乘法的结果填进去。两个值设成一样，避免线程数漂移引起吞吐波动。注意这是**每个消费者实例**的线程数——3 个实例就要么每实例 6 线程，要么接受总并发 54（然后被下面的限速器压住）。

只调线程数的问题在于它控制的是"能力"不是"速率"：下游变快时（中台深夜空闲，单条 20ms），18 个线程能冲到 900 TPS——超了中台白天的承诺容量三倍。所以还需要——

**板斧二：拉取节奏——中调。**

```java
consumer.setPullInterval(100);       // 每次拉取间隔 100ms
consumer.setPullBatchSize(32);       // 每次最多拉 32 条
consumer.setConsumeMessageBatchMaxSize(1);   // 业务侧仍单条消费，保证幂等粒度
```

每队列每秒拉 `1000/100 × 32 = 320` 条，8 个队列理论上限 2560/s——作为"总闸"仍然太粗。拉取参数适合限制"从 Broker 取货的节奏"防止本地缓冲堆爆（配合 `pullThresholdForQueue` 本地缓存上限），不适合精确限速。真正的精确控制是——

**板斧三：消费端限速器——精调。**

```java
private final RateLimiter limiter = RateLimiter.create(300);   // 全局 300 TPS

public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, ...) {
    limiter.acquire();          // 拿不到令牌就等，天然把消费压成匀速
    process(msgs.get(0));
    return CONSUME_SUCCESS;
}
```

在消费逻辑入口放一个令牌桶（单实例 Guava 即可；多实例则每实例 `300/实例数`，或用 Redis 令牌桶做全局速率——第五篇的工具箱在这里全用得上）。`acquire()` 阻塞会占住消费线程，所以线程数要按"限速后的实际 TPS"配，而不是反过来。

三板斧的分工一句话：**线程数决定"最多能跑多快"，拉取参数决定"取货节奏"，限速器决定"实际跑多快"。** 目标速率的精确保证永远来自限速器，前两者是为它准备合适的运行空间。

（RocketMQ 5.x 的 POP 消费模式把队列持有关系放到了 Broker 侧，消费能力不再被队列数硬绑——新项目值得评估，但三道乘法的思路不变。）

## 三、Kafka 对照：同一套算术，不同的旋钮

换成 Kafka，概念一一映射：队列→分区，消费组语义几乎相同。旋钮差异：

- **并发度**：标准玩法是"一个分区一个 consumer 线程"，18 并发 ≈ 18 个分区 + 18 线程（或更少线程 + 每线程多分区）。想要"分区数少、处理并发高"就得上"拉取线程 + 业务线程池"的两层模型——代价是位移提交复杂化：业务线程乱序完成，不能简单 `commitSync`，需要按分区维护已完成位移的水位，做不对就会丢消息或重复大片。
- **单次拉取量**：`max.poll.records`（默认 500）。**重逻辑消费必须调小**：500 条 × 60ms = 30 秒 > `max.poll.interval.ms`（默认 5 分钟虽够，但一旦下游抖动就超时）——超时的后果是被踢出消费组、触发 rebalance、分区易主重复消费，然后下一轮继续超时——**rebalance 风暴**，Kafka 消费故障里最经典的死亡螺旋。我们的场景配 `max.poll.records=32` 绰绰有余。
- **限速**：Kafka 客户端同样没有内置业务级限速，令牌桶方案原样平移。
- **排查清单**：消费 lag 涨了先查四件事——消费逻辑变慢（下游超时）、消费者 hang（线程 dump 看锁）、频繁 rebalance（日志关键字 `Attempt to heartbeat failed`）、单分区倾斜（key 分布不均，某分区独扛大流量）。

## 四、生产端与 Broker：别让上游成为瓶颈或风险

削峰场景生产端的压力窗口很短（洪峰几秒把 2 万条打进去），但两组权衡值得记录：

**吞吐 vs 延迟**：`batch.size`（攒批大小）与 `linger.ms`（攒批等待）是 Kafka 生产端的核心权衡——攒得越满吞吐越高、单条延迟越大。抢课发消息在用户同步路径上（发完才能返回"抢课成功"），**延迟优先**：`linger.ms` 保持 0~5ms，靠洪峰天然攒批。日志类场景才值得 `linger.ms=50` 换吞吐。压缩（`compression.type=lz4`）对小报名消息收益有限，消息体大时再开。

**吞吐 vs 可靠性**：上一篇说过报名消息丢不得，生产端必须 `acks=all` + 重试 + （Kafka）幂等生产者 `enable.idempotence=true`；RocketMQ 用同步发送而非 `sendOneway`。这些都会压低生产端峰值 TPS——**没关系**。削峰架构里生产端只要比洪峰快就行（几千 TPS 轻松达到），真正的速率控制在消费端。把可靠性预算花在生产端，把性能预算花在消费端，这是削峰场景的资源分配纲领。

Broker 侧记一条就够：副本同步能力（Kafka `num.replica.fetchers`）要跟上生产峰值，否则 ISR 收缩，`acks=all` 直接变慢甚至不可用——高峰期"生产突然变慢"的隐形元凶。

## 五、积压治理：当算术被现实打破

三道乘法算得再好，线上总有意外：中台限流了、消费者 OOM 了、某次发版把单条耗时从 60ms 拉到 600ms。堆积开始增长时的处置框架：

**先判断堆积的性质**：瞬时洪峰堆积（预期内，看消化时间是否在承诺 SLA 内）还是持续增长堆积（消费 < 生产，不处理永不收敛）。前者观察，后者行动。

**行动的优先级**：

1. **恢复消费速度**：多数堆积是消费端变慢引起的——先查下游（中台超时？DB 慢查询？），治好病根比扩容有效十倍。
2. **扩容**：消费者实例加到分区数上限；还不够就得动分区数（提前"宁多勿少"的红利在这兑现）。
3. **降级消费**：临时跳过非关键步骤（比如"写中台"改为标记后补偿重推），先把主流程消化掉——上一篇的状态机在这派上用场：CONFIRMED 拆成"落库完成"与"中台同步完成"两级。
4. **丢弃**：报名消息一条都不能丢，此选项不存在。但同一套系统里的埋点、通知类消息可以——**能不能丢，应该在设计消息时就分好 Topic，而不是堆积时现场纠结。**

最后一个隐蔽变量：**冷读**。堆积消化时读的是几分钟前的老消息，可能已不在 page cache，Broker 转为磁盘读，消费吞吐进一步下降——堆积越久越难消化的恶性循环。这是"堆积告警要趁早"的底层理由：晚 10 分钟处理，可能多花 30 分钟消化。

## 六、速查表：从目标到参数

| 你要什么 | 动哪里 |
|---|---|
| 确定并发度 | 目标 TPS × 单条耗时(s)，向上取整 |
| 确定分区/队列数 | ≥ 最大消费者实例数 × 2~3 留量，宁多勿少 |
| 精确限速（如 300 TPS） | 消费入口令牌桶（Guava/Redis），线程数按限速后 TPS 配 |
| 防 rebalance 风暴 | `max.poll.records` 调小，保证一批处理时间 ≪ `max.poll.interval.ms` |
| 生产端不丢消息 | `acks=all` + 幂等生产者 / RocketMQ 同步发送，接受峰值 TPS 损失 |
| 低延迟发送 | `linger.ms=0~5`，靠洪峰天然攒批 |
| 堆积告警阈值 | 堆积量 > 消费 TPS × 可容忍延迟秒数 |
| 堆积处置 | 查病根 → 扩容（≤分区数） → 降级消费 → （仅可丢消息）丢弃 |

## 七、小结，以及系列的收束

这一篇没有新架构，只有一根主线：**异步系统的速率是设计出来的，不是调出来的**。三道乘法（并发度、并行上限、消化时间）在纸上算清，参数只是誊写答案；速率的精确保证来自消费入口的限速器，而不是碰巧合适的线程数；积压的处置预案在设计消息分级时就该写好。

至此，《从抢课到秒杀》的主线走完了：从一个 20 个名额的内部抢课业务出发，我们建了两层防线（一、二、三篇），缝合了两个存储间的裂缝（四篇），纵深展开了限流（五篇），量化了同步的边界（六篇），付清了异步化的账单（七篇），最后把异步系统的速率钉在了目标值上（八篇）。回头看，贯穿八篇的其实是同一件事：**把"高并发"从一个吓人的形容词，还原成一组可测量、可计算、可选择的约束。**

还剩一个彩蛋（第九篇）：怎么用压测脚本和几条 SQL，向别人——以及向自己——证明这套系统真的不超卖。
