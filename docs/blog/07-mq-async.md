# 从抢课到秒杀（七）：异步化实战（上）——MQ 削峰的完整链路设计

> 本文是《从抢课到秒杀》系列的第七篇。上一篇给出了同步/异步的决策框架，
> 并预告了演进第一站：半异步。这一篇就把它设计到底——不是"加个 MQ"三个字，
> 而是把消息可靠性、消费幂等、状态管理、超时回补这一整串账单逐项付清。

## 一、设定舞台：假想需求升级

沿用上一篇的触发器，假设 TalentHub 遇到了真实的演进压力：

- 抢课扩展到集团级：热门课程库存从 20 涨到 **2 万**（在线课，名额约束来自平台容量）；
- 报名成功后要**同步写集团人力资源中台**——一个我们不可控、单机吞吐只有几百 TPS 的遗留系统。

按第六篇的公式算：2 万次合法落库 + 中台每秒几百的消化能力 = 洪峰要**几十秒到分钟级**才能消化完。同步链路里用户等不了这么久，四维清单翻转，异步化正式入场。

目标架构（半异步）：

```
用户请求
   ▼
限流 → Redis Lua 预扣（同步，不变）───► 失败：立刻返回"已抢完/已报名"
   │ 预扣成功
   ▼
发送报名消息到 MQ ───────────────────► 成功：返回"抢课成功，报名处理中"
   ▼（削峰缓冲区）
订单消费者（按自己的节奏）
   ▼
DB 落库（upsert + 条件 UPDATE，不变）→ 写中台 → 更新报名状态为"已确认"
```

注意有两样东西**刻意没变**：Redis 预扣脚本原封不动（用户仍然瞬间知道"抢没抢到"），DB 事务里那套 upsert + 条件 UPDATE 也原封不动——后面会看到，这两个"不变"正是整个改造能站住的地基。

## 二、MQ 凭什么能削峰：三个特性缺一不可

MQ 削峰不是玄学，它依赖三个具体特性，对应三个如果缺失就会翻车的点：

1. **消息堆积**：队列能吞下"洪峰 − 消费速率"的差值并持久化。开抢瞬间 2 万条消息涌入，消费者每秒处理 500 条，队列里最深堆积约 1.95 万条——MQ 的本职就是把这份堆积安全地存住。（这就是第五篇说的"漏桶思想在架构尺度上的放大"：桶 = 队列，恒定漏出 = 消费速率。）
2. **匀速消费**：消费端的速率由消费者自己决定，与生产速率解耦。下游中台每秒只能吃 300，消费者就配成 300——洪峰再大，中台看到的永远是匀速 300。速率具体怎么配准，是下一篇的整篇主题。
3. **至少一次投递**：Broker 保证消息不丢（代价是可能重复）。削峰场景丢一条消息 = 用户"抢到了却没报上"，比重复严重得多——所以方向必然是"不丢但可能重"，把"重"留给消费端幂等解决。

## 三、第一个硬问题：预扣和发消息，不是原子的

同步链路里，Redis 预扣和 DB 落库之间的裂缝靠"同步回补 + 反查"缝合（第四篇）。异步化后裂缝换了位置：**Redis 预扣成功 → 发送消息**，这两步同样不是原子的。逐种失败分析：

- **发送明确失败**（Broker 拒绝、超时前收到错误）：和第四篇分支 B 同构——同步回补预扣（rollback.lua，幂等），返回"系统繁忙"。用户重抢即可。
- **发送结果未知**（超时无响应）：和第四篇分支 C 同构——消息可能已入队。**不能盲目回补**：万一消息在队里，回补后消费者又把单落了，名额凭空多放一个。正确姿势是重发（消息带唯一 ID，消费端幂等兜住重复），重发再失败才回补并告警。
- **应用发完消息就崩溃**：消息在队里，什么都不用做——这正是异步化买到的故障隔离：请求已经"安全上岸"。

会发现决策逻辑和第四篇的三分支惊人地相似。**这不是巧合：任何"两个存储/系统间的非原子写"都长这个样子**——确定失败则回滚、结果未知则先查证或重试、偏保守方向倾斜。第四篇练出的肌肉，这里直接复用。

更彻底的方案是 **RocketMQ 事务消息**：半消息 → 执行本地逻辑（预扣）→ commit/rollback，Broker 还会对悬挂的半消息回查。它把上面的手工缝合制度化了，代价是引入回查接口的实现与运维。中小规模用"重发 + 幂等 + 回补"的手工方案完全够；预扣逻辑复杂到难以回查时再上事务消息。

## 四、第二个硬问题：消费幂等——旧防线的新岗位

至少一次投递 + 发送端重发，意味着消费者**必然**会收到重复消息。消费逻辑必须幂等。

这里是整个改造最愉快的部分：**幂等防线早就建好了**。回看消费者要执行的落库逻辑——正是第三篇那个事务：

```
upsert（ON CONFLICT ... WHERE status = 2）  → affected 0 = 该用户已有有效报名
条件 UPDATE（stock > 0）                    → 防超卖照旧
```

同一条报名消息消费两次：第一次正常落库；第二次 upsert 返回 0，直接 ack 掉消息、不再扣库存——**天然幂等，一行代码不用加**。第三篇设计 upsert 时考虑的是"并发双请求穿过 Redis 判重"，如今它兜住的是"MQ 重复投递"——好的不变量设计，会在你意想不到的地方第二次发工资。

唯一要新增的是消费失败的分类处理：

- **业务性失败**（DB 售罄，affected 0）：不重试（重试一万次也是售罄），走"报名失败"流程——更新状态、回补预扣名额；
- **技术性失败**（DB 超时、中台不可达）：重试（RocketMQ 默认梯度重试），超过上限进**死信队列** + 告警，人工介入。

  死信队列必须有人认领。它不是垃圾桶，是"系统自己搞不定、承诺过用户却没兑现"的清单——每一条都对应一个抢到名额却没报上名的用户。

## 五、第三个硬问题："报名处理中"是一个新的业务状态

同步时代，接口返回即终态。异步化后，"抢到了"和"报上了"之间出现一段真空，必须用状态机把它管起来：

```
PENDING（预扣成功，消息已发） → CONFIRMED（落库+中台完成）
                              → FAILED（业务性失败，名额已回补）
```

配套三件事，一件都省不掉：

1. **状态的存储与写入**：预扣成功时写入 PENDING（可先记 Redis，消费成功后落库为准），消费者是唯一的状态推进者。
2. **查询通道**：轮询接口（`GET /enrollments/status`，前端 2 秒一查，配指数退避）起步就够；体验升级再上 SSE/WebSocket 推送。别小看这个接口——异步化后它就是用户焦虑的唯一出口。
3. **前端话术**：**"排队中"不等于"结果未知"**。半异步的妙处在于预扣结果就是最终结果的可靠预告（PENDING → CONFIRMED 的转化率应 >99.9%），所以话术可以自信："抢课成功，报名确认中"——而不是让用户以为自己还在赌。这个差别决定了用户会不会疯狂刷新页面，把状态查询接口变成新的洪峰。

## 六、第四个硬问题：超时兜底——异步世界的对账任务

最后一块拼图：消息如果**长时间没被消费**（消费者全挂了、死信了、或消息真的丢了），用户的名额被预扣着、状态停在 PENDING，既没确认也没释放。需要一条超时兜底链路：

- **定时扫描**：每分钟扫出 PENDING 超过 N 分钟的记录 → 反查 DB（又是第四篇的反查！）——已落库则补推状态为 CONFIRMED；未落库则回补预扣、置为 FAILED、通知用户"报名未成功，名额已释放"。
- 或用 **RocketMQ 延时消息 / 死信 TTL** 实现同样语义，省掉扫描但多一份消息链路的复杂度。

加上它，异步链路的兜底结构和同步时代形成完整对偶：

| | 同步时代（第四篇） | 异步时代（本篇） |
|---|---|---|
| 毫秒级主路径修复 | DB 失败同步回补 | 发送失败同步回补 |
| 结果未知时 | 反查 DB 再决定 | 重发消息 / 反查 DB 再决定 |
| 分钟级兜底 | 库存对账任务 | PENDING 超时扫描 |
| 审计 | reconcile_log | 死信队列 + 状态流转记录 |

架构变了，**"确定才动手、未知先查证、兜底必审计"的纪律一条没变**。

## 七、小结：账单付清了吗

回头数一数"加个 MQ"实际付出的东西：

1. 发送可靠性：失败回补 / 未知重发的缝合逻辑（或事务消息）；
2. 消费幂等：复用 upsert 防线（近乎免费，前提是当初设计对了）；
3. 失败分类：业务性不重试、技术性梯度重试 + 有人认领的死信；
4. 状态机：PENDING/CONFIRMED/FAILED 的存储、查询接口、前端话术；
5. 超时兜底：PENDING 扫描 + 回补通知。

换来的：下游中台永远只见匀速流量；DB/中台故障期间用户照常"抢到"，请求在队列里安全等待；吞吐瓶颈从"最慢环节"变成"消费者数量 × 单条耗时"——一个可以用钱和配置解决的问题。

而"可以用配置解决"恰恰是下一篇的主题：消费者线程开多少、拉取批量配多大、生产端 batch 和 linger 怎么权衡，怎么让这套异步系统精确跑在你想要的 QPS/TPS 上——异步化实战（下）。
