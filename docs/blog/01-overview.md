# 从抢课到秒杀（一）：toB 类秒杀的业务建模与总体架构

> 本文是《从抢课到秒杀：一个 toB 类秒杀系统的设计与演进》系列的第一篇。
> 系列以我实现的开源演示项目 **TalentHub**（Spring Boot 3 + PostgreSQL + Redis + Vue 3）为贯穿案例，
> 每个设计断言都能在代码仓库里找到对应实现。

## 一、一个被低估的场景：内部系统里的"类秒杀"

我曾在中国移动的人力资源系统中接触过培训报名业务：公司发布一门热门培训课程，名额 20 个，报名开放的那一分钟里，几百上千名员工同时点击"报名"。

这个场景乍看平平无奇——并发几百而已，谈什么架构？但它有一个和电商秒杀完全相同的硬约束：

> **名额有限，绝对不能超卖。**

20 个名额的线下课，报进来 25 个人，教室坐不下、讲师课酬超预算、多出来的 5 个人要被 HR 逐个打电话劝退——在 toB 系统里，超卖不是资损问题，是**信任问题**。内部系统一旦让员工觉得"规则会出错"，后面每一次报名都会被质疑。

于是我把这个业务抽象出来，做成了 TalentHub 这个演示项目。这个系列会完整拆解它的设计、实现与演进方向。

## 二、类秒杀 ≠ 秒杀：先把业务建模做对

很多人拿到"抢课"需求，第一反应是照搬电商秒杀的全套架构：CDN 动静分离、答题验证码、库存分桶、MQ 异步下单……这是本系列想反对的第一件事：**架构设计的起点是业务约束，不是技术清单。**

把抢课和电商秒杀放在一起对比，差异非常清晰：

| 维度 | 电商秒杀 | 内部抢课 |
|---|---|---|
| 峰值并发 | 数十万 ~ 百万 QPS | 数百 ~ 数千 QPS（员工总数有限） |
| 超卖容忍 | 不可超卖 | **同样不可超卖** |
| 少卖容忍 | 尽量不少卖（资损） | 可短暂容忍（补偿修复即可） |
| 黑产对抗 | 核心难题（脚本、黄牛、僵尸号） | 几乎没有（实名员工账号） |
| 结果时效 | 可接受"排队中"异步出结果 | 员工期望**点完立刻知道** |
| 公平性要求 | 先到先得即可 | 先到先得即可，但要经得起 HR 审计 |

两个关键结论从表里直接掉出来：

1. **并发量级差 2~3 个数量级**。电商秒杀架构里对抗百万 QPS 的那些手段（分桶、答题、独立集群），在这里是负收益的复杂度。
2. **约束的"形状"不同**：这里是"超卖零容忍 + 少卖可容忍 + 结果要即时"。这个形状直接决定了后面所有的技术选型。

由此得到整个系统的**第一性设计原则**，它会贯穿本系列每一篇：

> **任何不一致，只允许表现为"少卖"，绝不允许"超卖"或"一人多单"。**

这句话的工程含义是：所有涉及两个存储（Redis 与数据库）的操作，中间态必须偏向保守——宁可名额被暂时"冻结"（少卖，可由补偿任务修复），也不能让两份数据都放行同一个名额（超卖，覆水难收）。

## 三、总体架构：两层防线

TalentHub 的核心链路是一个经典的两层防线结构：

```
用户请求
   │
   ▼
┌─────────────┐  接口限流（Lua 固定窗口：课程维度 QPS + 用户维度防连点）
│   应用层     │  登录态 / 报名时间窗校验
└──────┬──────┘
       ▼
┌─────────────┐  enroll.lua 原子执行三件事：
│    Redis     │  ① 用户去重(SISMEMBER) ② 库存判断 ③ 预扣(DECR+SADD)
└──────┬──────┘  无效请求在此终结，不触达数据库
       ▼ 仅"预扣成功"的请求
┌─────────────┐  单事务：INSERT ON CONFLICT 报名 + 条件 UPDATE 扣库存
│ PostgreSQL  │  行锁 + stock > 0 + 唯一约束 —— 超卖与重复报名的最终防线
└──────┬──────┘
       │ DB 失败 ──► 同步回补 Redis（rollback.lua，幂等）
       ▼
┌─────────────┐
│  对账补偿任务 │  定时核对 Redis 与 DB 库存，以 DB 为准单向修正（纯兜底）
└─────────────┘
```

理解这个架构的正确方式，不是记住每一层"做什么"，而是想清楚每一层"**挂了会怎样**"：

| 层 | 职责 | 失效后果 |
|---|---|---|
| 限流层 | 挡掉超量与连点请求，保护下游 | 请求多打一些到 Redis，Redis 扛得住 |
| Redis + Lua | 挡掉重复用户与超库存请求，保护 DB | 请求打到 DB，压力上升，但**不会超卖** |
| PostgreSQL | 权威数据源：条件更新防超卖，唯一约束防重单 | 无——这是最后防线，它的正确性不依赖上游 |
| 对账任务 | 修复极端场景下 Redis 与 DB 的残留差异 | 差异修复变慢，表现为短暂少卖 |

注意这个结构的精髓：**上面三层每一层都可以失效，而"不超卖"这个硬约束始终由最底层的一条 SQL 保证**：

```sql
UPDATE course SET stock = stock - 1
WHERE id = ? AND stock > 0 AND status = 1;
-- affected rows = 0 即售罄，事务回滚
```

行锁 + 条件更新，数据库天然串行化同一课程的扣减。哪怕限流全失效、Redis 整个宕机、请求全量裸奔到数据库，最坏结果也只是 DB 压力大、响应变慢——多卖一个名额是不可能的。**上层防线全部是性能优化，只有数据库这层是正确性保证**。分清这两者，是这类系统设计的分水岭。

反过来，Redis 层的价值也因此变得纯粹：在正常运行时，它把 99% 的无效请求（重复报名的、库存已尽的）挡在数据库之外，让最终防线只需要处理"大概率会成功"的请求。库存 20 的课程，最终到达数据库的请求只有 20 多个，单行热点根本不构成压力。

## 四、三个"不做"的决策

比"做了什么"更能体现设计判断的，是"明确不做什么"。TalentHub 有三个刻意的"不做"：

**不做 MQ 异步下单。** 员工期望点完立刻知道结果，而同步链路在这个量级下毫无压力。引入 MQ 意味着要额外维护：消息可靠性（发送确认、持久化、重试、死信）、消费幂等、下单结果的状态查询接口、超时未消费的名额回补……这是一整套新的复杂度，换来的削峰能力在数百 QPS 的场景下用不上。（第 6~8 篇会专门讨论：什么信号出现时才应该引入 MQ，以及引入后怎么把它调到想要的 QPS/TPS。）

**不做库存分桶。** 分桶（把一行库存拆成 N 行随机扣减）解决的是单行热点的锁竞争，适用于单商品扣减 TPS 上万的场景。这里最终到达 DB 的写请求约等于库存量，热点不存在。

**不做分布式事务框架。** Redis 与 DB 的一致性用"同步回补 + 幂等脚本 + 对账兜底"的最终一致方案解决（第 4 篇详述），成本比 Seata 之类的框架低一个量级，且故障模式更容易推理。

这三个"不做"共同指向一个立场：**演示系统也好，生产系统也好，复杂度应该被业务量级"挣"出来，而不是被技术履历表堆出来。**

## 五、技术栈与系列导读

TalentHub 的技术栈刻意选得朴素：

- **后端**：Java 17 · Spring Boot 3.3 · MyBatis（SQL 全部显式写在 XML）· PostgreSQL 16 · Spring Data Redis（Lua 脚本随应用启动加载）· `@Scheduled` 调度
- **前端**：Vue 3 + TypeScript + Arco Design Vue（抢课页有实时库存、倒计时与状态反馈）

朴素的另一面是：每一处关键设计都经得起放大检视。本系列后续各篇会逐层展开——

- **第 2 篇** Redis + Lua：为什么 `GET 判断 + DECR` 有竞态、预扣脚本如何把去重/判断/扣减做成原子操作、回补脚本怎样做到天然幂等；
- **第 3 篇** PostgreSQL 防超卖：条件 UPDATE 与 `SELECT FOR UPDATE` 的锁持有对比、`ON CONFLICT` upsert 如何消灭三个业务分支、MVCC 下热点行的表膨胀治理；
- **第 4 篇** 一致性工程：DB 失败的三个分支（尤其是"结果未知"时先反查再回补的超时语义）、对账任务的边界感；
- **第 5 篇**（衍生）服务限流详解：从系统里 30 行的限流 Lua，讲透四大限流算法与单机/分布式方案选型；
- **第 6~8 篇** 演进方向：同步 vs 异步的决策框架、MQ 削峰链路设计、以及怎么让 MQ 精确跑在你想要的 QPS/TPS 上。
