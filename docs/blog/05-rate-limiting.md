# 从抢课到秒杀（五）：服务限流详解——从 30 行 Lua 说开去

> 本文是《从抢课到秒杀》系列的第五篇，也是第一篇"衍生篇"：
> 从 TalentHub 里一段其貌不扬的限流代码出发，把服务限流这个主题一次讲透。
> 前四篇的系统实录不是本篇的前置——你可以把它当一篇独立的限流综述来读。

## 一、引子：系统里真实的两级限流

TalentHub 的抢课接口前面挂着两级限流，实现是同一段 30 行不到的 Lua（`rate_limit.lua`）：

```lua
-- 固定窗口限流
-- KEYS[1] = 计数 key   ARGV[1] = 窗口秒数   ARGV[2] = 窗口内上限
-- 返回值: 1=放行  0=超限

local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if count > tonumber(ARGV[2]) then
    return 0
end
return 1
```

同一段脚本，喂不同的 key 和参数，就是两级不同的限流：

| 级别 | key | 窗口/上限 | 目的 |
|---|---|---|---|
| 课程维度 | `rl:course:{courseId}` | 1 秒 / 100 次 | 保护数据库，挡掉超量洪峰 |
| 用户维度 | `rl:user:{userId}:{courseId}` | 2 秒 / 1 次 | 防连点、防脚本刷 |

阈值怎么定的？课程级的 100 QPS 不是压测压出来的，是**业务反推**的：库存 20 的课程，放行 100 个请求进入 Redis 预扣，成功的最多 20 个，剩下 80 个被预扣层用一次 O(1) 判断打发掉——阈值 ≈ 库存 × 若干倍，既给了失败重试的余地，又保证到达数据库的请求不会超过库存量级。**限流阈值可以来自压测，也可以来自业务量纲，后者常常更稳定**（库存不变，阈值就不用跟着机器规格重调）。

还有一个立场问题，比算法更重要。限流脚本执行失败（Redis 抖动）时，这套系统选择 **fail-open——放行**：

```java
} catch (Exception e) {
    // 限流是保护手段而非正确性手段：Redis 异常时放行，由 DB 最终防线兜底
    log.warn("限流脚本执行失败，本次放行: key={}", key, e);
    return;
}
```

因为在这套架构里，正确性由数据库的条件 UPDATE 兜底，限流只是性能保护——限流挂了，最坏是 DB 累一点。但注意这个结论**不可移植**：如果你的限流保护的是没有兜底的脆弱下游（比如按调用量计费的第三方接口），fail-closed 才是对的。**决定 fail-open 还是 fail-closed 的，不是限流组件本身，而是它身后有没有防线。**

好，引子结束。这段代码用的"固定窗口"是四大限流算法里最朴素的一个——它够用，但它的缺陷、以及其它三种算法各自解决了什么，值得完整过一遍。

## 二、四大限流算法

### 1. 固定窗口（Fixed Window）

把时间切成等长窗口，每个窗口维护一个计数器，满了就拒，窗口切换时清零——正是上面那段 Lua。

- **优点**：实现最简单（一个计数器 + 一个过期时间），内存开销最小，语义直白。
- **致命缺陷：窗口边界突刺**。限流 100/秒时，第 1 秒的最后 100ms 进来 100 个请求（合法），第 2 秒的前 100ms 又进来 100 个（窗口刚重置，也合法）——200ms 内实际通过了 200 个请求，瞬时压力是名义限额的两倍。

TalentHub 敢用它，是因为下游扛得住 2 倍突刺（Redis 预扣是 O(1) 操作，翻倍毫无压力）。**下游余量充足时，固定窗口的简单就是它最大的优点**；下游脆弱时，才需要为平滑付出复杂度。

### 2. 滑动窗口（Sliding Window）

解决突刺的直接思路：别让窗口"跳变"，让它"滑动"——统计"此刻往前一秒"内的请求数，而不是"本自然秒"内的。两种常见实现：

- **Redis ZSET**：每个请求以时间戳为 score 加入有序集合，判断前先 `ZREMRANGEBYSCORE` 清掉窗口外的旧记录，再 `ZCARD` 计数。精确，但每个请求都占一条内存记录，高 QPS 下开销可观。
- **分格计数**：把 1 秒切成 10 个 100ms 的小格，每格一个计数器，滑动时加总最近 10 格。精度与内存的折中方案，也是多数生产实现（如 Sentinel 的 `LeapArray`）的选择。

滑动窗口消灭了边界突刺，但仍不"平滑"：窗口配额可以在窗口开头被瞬间耗尽，之后整段时间全拒。它管住的是"总量"，管不住"节奏"。

### 3. 漏桶（Leaky Bucket）

换个思路：不控制"进"，控制"出"。请求先进桶（队列），系统以**恒定速率**从桶里取出处理；桶满则拒。

- **优点**：输出速率绝对恒定，是最强的"流量整形"——无论上游多疯狂，下游看到的永远是匀速请求。
- **缺点**：完全无法利用突发容量。下游明明空闲，请求也要在桶里排队等固定节拍；且请求要么排队（增加延迟）要么溢出（被丢弃）。

眼熟吗？**漏桶就是 MQ 削峰的算法内核**——消息堆积在队列（桶），消费者匀速消费（恒定漏出）。第七篇讲 MQ 削峰时，你会发现那是漏桶思想在架构尺度上的放大。

### 4. 令牌桶（Token Bucket）

漏桶的镜像改进：以恒定速率往桶里**放令牌**，请求来了取令牌，有令牌立刻放行，没有则拒/等待。桶的容量就是允许的**突发额度**——空闲时攒下的令牌，可以在突发时一次性花掉。

- **优点**：兼顾平均速率控制与突发容忍，是互联网场景的默认选择（Guava、Nginx、Sentinel 预热模式的底层都是它或其变体）。
- **两个坑**：一是**冷启动误杀**——服务刚启动桶是空的，正常流量也会被拒，Guava 的 `SmoothWarmingUp` 预热模式就是为此设计（启动初期令牌发放速率渐进爬升）；二是两个参数（桶容量、放令牌速率）的调校需要理解业务的突发形态，配错了要么突刺打穿下游、要么白白拒掉合法流量。

### 一张对比表

| | 固定窗口 | 滑动窗口 | 漏桶 | 令牌桶 |
|---|---|---|---|---|
| 实现复杂度 | 最低 | 中 | 中 | 中 |
| 内存开销 | 最小 | ZSET 大 / 分格小 | 队列深度 | 最小 |
| 边界突刺 | **有（2 倍）** | 无 | 无 | 无 |
| 突发容忍 | 窗口内可 | 窗口内可 | **完全不容忍** | **可控容忍（桶容量）** |
| 输出平滑度 | 差 | 中 | **绝对平滑** | 平均平滑 |
| 典型场景 | 下游有余量的粗防护 | 精确计数限额（API 配额） | 严格整形（保护脆弱下游） | 通用默认选择 |

## 三、单机限流工具箱

算法之上，Java 生态的现成轮子：

**Guava RateLimiter**——令牌桶的教科书实现，两行上手：

```java
RateLimiter limiter = RateLimiter.create(100);          // 100 QPS
if (!limiter.tryAcquire()) { throw new BizException(RATE_LIMITED); }
// 预热模式：3 秒内速率从冷启动渐进爬到 100 QPS，避免误杀
RateLimiter warm = RateLimiter.create(100, 3, TimeUnit.SECONDS);
```

适合"进程内保护一段本地资源"的场景。局限：单机、无监控、功能单一（只有令牌桶）。

**Bucket4j**——更工程化的令牌桶：支持多带宽叠加（如"每秒 100 且每分钟 3000"）、多种后端（内存/Redis/Hazelcast，天然可升级为分布式）、能对接 Prometheus/Grafana。适合需要"限流规则可组合、指标可观测"的中型项目。

**Sentinel**——阿里开源的流量治理全家桶：限流之外还有熔断降级、热点参数限流（对"某个具体课程 ID"单独限流——正是抢课场景的形状）、系统自适应保护（按 CPU/负载动态收紧），配 Dashboard 动态下发规则。适合微服务体系里做统一流量治理。代价是引入一整个组件的运维与学习成本。

选择的朴素标准：**保护一段代码用 Guava，保护一个服务用 Bucket4j，治理一个体系用 Sentinel。**

## 四、分布式限流

单机限流有个前提：配额可以按实例均分。总配额 1000 QPS、10 个对等实例、负载均衡足够均匀，那每台限 100 就完事——**这种情况请坚持单机限流**，没有网络往返、没有外部依赖，又快又稳。

均分假设不成立时（实例数弹性伸缩、流量按用户哈希倾斜、配额本身是全局语义如"每用户每天 100 次"），才需要分布式限流。事实标准是 **Redis + Lua**：计数状态放 Redis（单线程天然解决集群并发计数），判断与更新用 Lua 保证原子——TalentHub 那段固定窗口就是最小实现。三个实践注意点：

1. **集群模式下脚本的 key 必须落同一节点**——多 key 脚本用 hash tag（`rl:{course:1}:...`）保证同槽。
2. **主从异步复制会丢计数**——主挂了、从顶上，窗口计数可能回退，短时间多放一些流量。限流对精度的容忍远高于分布式锁，通常可接受；不能接受就要上 Redlock 级别的代价，先问值不值。
3. **别忘了限流器自身的开销**——每个请求多一次 Redis 往返。放在网关层批量做，或本地预扣配额 + 异步同步（如 Sentinel 集群流控的 token server 模式），是高 QPS 下的优化方向。

现成方案：**Redisson `RRateLimiter`**（分布式令牌桶，底层就是 Lua）、**Spring Cloud Gateway `RedisRateLimiter`**（网关层令牌桶）、**Sentinel 集群流控**。自己写 Lua 和用轮子之间怎么选？规则简单固定（像抢课这种"一档配置走天下"）自己写反而透明；规则多变、需要动态下发时用轮子。

## 五、算法之外：限流的三个工程维度

限流文章大多止步于算法，但生产事故大多出在算法之外。

**① 限流对象是分层的。** 一套成熟系统的限流不是一个点，是一条纵深：

```
接入层  Nginx/网关     —— 按 IP、按接口的粗粒度总闸
应用层  业务限流       —— 按课程、按用户的细粒度业务闸（TalentHub 的两级 Lua）
资源层  连接池/线程池   —— 最后的物理闸：HikariCP 上限 30 就是并发限流
```

第三层最容易被忽视：**连接池、线程池本质上都是并发数限流器**。TalentHub 把报名接口的连接池收紧到 30，就是在说"无论上面放进来多少，同时打到数据库的最多 30"。上层限流失效时，是它在兜底性能——层与层的关系，和第一篇的防线思维一脉相承。

**② 拒绝策略是产品设计。** 请求超限后怎么办，有三种姿势：

- **直接拒绝**：返回 429 语义 + 明确话术。TalentHub 的选择——抢课场景下用户对"人多"有预期，"当前抢课人数过多，请稍后重试"甚至强化了稀缺感。
- **排队等待**：`limiter.acquire()` 阻塞到拿到配额。适合内部调用削峰，坚决不要用在面向用户的同步接口上（把限流变成了雪崩挂起）。
- **降级返回**：给兜底数据（缓存快照、默认值）。适合读接口，写接口没有"降级写"一说。

**③ 阈值需要维护，而不是配完就忘。** 三个来源交叉验证：压测得出的下游容量上限、业务量纲反推（本文开头的"库存 × 系数"）、线上观测（限流触发率长期为 0 说明阈值虚高形同虚设，频繁触发说明容量或阈值有一个错了）。更进一步是与降级联动——TalentHub 的设计文档里就写着：Redis 故障降级直连 DB 时，限流阈值自动下调。**阈值是系统状态的函数，不是常量。**

## 六、选型速查表

| 场景 | 推荐方案 |
|---|---|
| 进程内保护一段热点代码 | Guava RateLimiter（预热模式防冷启动误杀） |
| 单体/小集群，配额可按实例均分 | 单机令牌桶（Guava / Bucket4j），别上分布式 |
| 全局语义配额（每用户每天 N 次） | Redis + Lua 固定/滑动窗口，或 Redisson RRateLimiter |
| 网关层统一限流 | Spring Cloud Gateway RedisRateLimiter / Sentinel 网关插件 |
| 微服务体系流量治理（限流+熔断+热点） | Sentinel + Dashboard |
| 保护脆弱下游，要求绝对匀速 | 漏桶 / 直接上 MQ（见第七篇） |
| 下游余量充足的粗防护 | 固定窗口，30 行 Lua 足矣（本文引子） |

回看 TalentHub 的选择就清楚了：下游（Redis 预扣）余量充足 → 固定窗口的突刺无害 → 选最简单的实现；正确性有数据库兜底 → fail-open；配额是业务全局语义（每课程 100 QPS）→ 放 Redis 做分布式计数。**每一项都不是"最好的技术"，而是约束链条推出来的那一个**——这也是整个系列反复出现的方法论。

下一篇回到主线，讨论一个更大的分岔：当并发涨到同步链路扛不住时，异步化（MQ）值不值得上、什么时候上——同步与异步的架构决策框架。
